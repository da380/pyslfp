# Contributing

## Development setup

Install the package with its development dependencies, then install the git
hooks:

```bash
poetry install --with dev
poetry run pre-commit install --hook-type pre-commit --hook-type pre-push
```

Both hook types are needed. On `git commit`, `pre-commit` runs Ruff (linting
with `--fix`, then formatting), `nbstripout`, and a few checks on the YAML and
TOML files; on `git push` it runs the test suite. It also refuses commits made
directly on `main`.

The same hooks run in CI — the `Lint (pre-commit)` job reads this very
`.pre-commit-config.yaml` — so anything that passes locally passes there. To
check the whole repository by hand rather than waiting for a commit:

```bash
poetry run pre-commit run --all-files
```

## Tests

```bash
poetry run pytest             # the fast suite, which is the default
poetry run pytest -m slow     # only the slow tests
poetry run pytest -m ""       # everything
```

The slow tests are the ones that read the real datasets from Zenodo: the ICE-NG
histories, the IHO seas and HydroBASINS shapefiles, the GLOSS tide gauge
network. They are deselected by default because the first run downloads several
hundred megabytes. CI runs the fast suite on every pull request into `main`, and
again whenever the pull request's branch is pushed to; a pull request is merged
only once it passes, so `main` is always in a working state. CI does not run on
pushes to `develop`, so run the suite locally before pushing (the pre-push hook
does). The whole suite, slow tests included, is the `full-tests` job. It runs
automatically on every release (see below), and on demand from the Actions tab
(Actions -> CI -> Run workflow) on any branch, which is worth doing after a
change to the regions, ice or tide gauge code.

Note that `test_iceng_real_data_integration` is guarded by a `skipif` that looks
for the ICE-7G directory when the module is imported. On a machine that has
never downloaded it, that test reports as skipped rather than failing, so a
green `-m slow` run does not by itself mean it ran.

## Documentation

```bash
poetry run sphinx-build -b html -W --keep-going docs/source docs/build/html
```

The `-W` matches the CI docs job, which treats warnings as errors; Read the
Docs deliberately does not (see `.readthedocs.yaml`).

The API reference pages are generated by `sphinx-apidoc`, which `docs/source/conf.py`
runs on `builder-inited`. They are build output, not source: they are gitignored,
and adding, renaming or moving a module needs no action beyond the rename.

`docs/apidoc_templates/package.rst.jinja` is the stock apidoc package template
with one change, which is explained in the file: the package-level `automodule`
is rendered with no options, so that the classes re-exported by each
`__init__.py` are documented once rather than twice.

## Tutorials and notebooks

The tutorials are the scripts in `tutorials/scripts`, written in cells (`# %%`,
with `# %% [markdown]` for prose) so that they run from the command line or cell
by cell in an editor. The slow tests run every one of them headless.

Each script has a notebook in `tutorials/notebooks`, generated from it by
`tutorials/make_notebooks.py`; these are what the Colab links in the README
open. Edit the scripts, never the notebooks. The `tutorial-notebooks` pre-commit
hook regenerates the notebooks whenever a file under `tutorials/` changes, and
stops the commit when one was stale so that the regenerated notebook can be
added; in CI the same hook fails a pull request whose notebooks were not
regenerated. To regenerate by hand:

```bash
poetry run python tutorials/make_notebooks.py
```

A script must begin with a cell marker, and every line of a markdown cell must
be a comment. The generator adds one cell to each notebook, which installs the
library on Colab and does nothing elsewhere.

The notebooks are committed as source, never as a record of a particular run.
`nbstripout` enforces this: it removes cell outputs and execution counts, and
renumbers cell ids so that merely opening a notebook does not dirty the working
tree. Committing outputs would add megabytes of base64 images and make every
diff unreadable.

## Ruff versions

`ruff` appears twice: as a dev dependency in `pyproject.toml` and as the `rev`
of the `ruff-pre-commit` hook. The two must be bumped together. If they drift
apart, the hook and `poetry run ruff` disagree about formatting and reformat the
same files back and forth between commits.

## Data

The datasets live on Zenodo, on a versioned record. `RECORD_ID` in
`pyslfp/data/downloader.py` names the version the library fetches, and must be
updated to the new record id when a new version is published. The same module
holds two tables that must be kept in step with the record by hand: `DATASET_FILES`,
the name of each zip on the record, and `FOLDER_MAP`, the folder each zip
extracts to. The zip and its folder need not share a name, so neither table is
derived from the other. A copy of the file names lives in
`tests/data/test_downloader.py`, and the slow test there checks the record's
own listing. The documentation links to the concept record
(<https://zenodo.org/records/19494463>) rather than to a version, since the
concept record always resolves to the latest version and so never needs
updating.

## Release process

This outlines the steps to publish a new version of `pyslfp` to PyPI.

### Prerequisites

- All code changes for the new version have been merged into `main`.
- `main` is stable and its pull request checks have passed. The slow tests need
  not be run by hand: the release runs them before anything is published.

### 1. Create a version bump pull request

The version number in `pyproject.toml` is updated in its own branch and pull
request.

1.  **Create a branch** from `main`:
    ```bash
    git checkout main
    git pull origin main
    git checkout -b release/vX.Y.Z  # Replace X.Y.Z with the new version
    ```

2.  **Update the version number** in `pyproject.toml`:
    ```toml
    [project]
    name = "pyslfp"
    version = "X.Y.Z"  # Change this line
    # ...
    ```

3.  **Commit and push**:
    ```bash
    git add pyproject.toml
    git commit -m "Bump version to X.Y.Z"
    git push origin release/vX.Y.Z
    ```

4.  **Open a pull request** from `release/vX.Y.Z` to `main`, titled "Release vX.Y.Z".

### 2. Review and merge

- The pull request triggers the CI workflow.
- Once the checks have passed and the pull request is approved, merge it into `main`.

### 3. Publish the release on GitHub

Merging does **not** publish the package. Creating a GitHub Release is what
triggers the release workflow, `publish.yml`.

1.  **Go to the repository homepage** on GitHub.
2.  **Click "Releases"** in the right-hand sidebar.
3.  **Click "Draft a new release"**.
4.  **Create a tag:** type the new version as `vX.Y.Z` and choose
    "Create new tag: vX.Y.Z on publish". The tag must match the version in
    `pyproject.toml`; `publish.yml` checks this and fails the release if it does
    not, because PyPI will not let a version be re-uploaded once it is wrong.
5.  **Target `main`.**
6.  **Add a release title:** the tag name, `vX.Y.Z`.
7.  **Write release notes** summarising the changes.
8.  **Click "Publish release"**.

The release workflow then checks that the tag matches the version, runs the
whole of CI on the tagged code (linting, the fast suite on all three platforms,
the documentation build and the slow tests), and only if every job passes
builds the package and uploads it to PyPI. The `Release` badge in the README
shows the outcome of the latest release.

If a check fails, nothing has reached PyPI, so the version number is still free.
Delete the GitHub release and its tag (`git push --delete origin vX.Y.Z`), fix
the problem through a pull request into `main` as usual, and publish the release
again with the same tag.
